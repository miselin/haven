# Haven Agent Guide

## Repository scope

- The maintained compiler is the OCaml implementation under `src/`. Treat it as the default target for compiler work.
- `legacy/` contains the deprecated C compiler. Change or validate it only when the task explicitly concerns the legacy implementation or compatibility with it.
- `src-new/` is the experimental self-hosted compiler. Do not assume changes there are part of the mainline implementation.
- Keep patches focused. Preserve unrelated working-tree changes and do not commit generated build output.

## Source layout

The mainline compiler is organized as follows:

- `src/lib/lexer`, `src/lib/token`, and `src/lib/parser`: tokenization and Menhir parsing.
- `src/lib/cst`: concrete syntax tree representation and source-preserving helpers.
- `src/lib/ast`: surface/core AST conversion, imports, analysis passes, and LLVM emission.
- `src/bin`: the compiler, formatter, AST tool, and language server executables.
- `src/test`: the OCaml regression suite.
- `docs` and `examples`: language documentation and executable Haven examples.

For language changes, follow the full path from syntax through lowering, analysis, and code generation. Parsing successfully is not enough evidence that a feature is correct at runtime.

## Generated files

- Edit `src/dune-project`, not `src/haven.opam`; the opam file is generated by Dune.
- Edit `src/lib/parser/grammar.mly`, not parser artifacts under `_build`.
- Do not edit or commit `_build`, `result`, `build-*`, generated LLVM/assembly/bitcode, executables, or test images.
- Dune stanzas use explicit module lists. When adding an OCaml module, update the appropriate `dune` file and the test runner when applicable.

## OCaml style

- Use the repository's `src/.ocamlformat` configuration as the formatting authority. Do not hand-align code against `ocamlformat` output.
- Use `snake_case` for values, functions, record fields, and type names; use `CamelCase` for modules and constructors.
- Prefer small, explicit functions and direct pattern matching. Keep transformations close to the AST type or pass they operate on.
- Prefer exhaustive matches for closed variants. Use a wildcard only when newly added constructors should intentionally share the same behavior.
- Add type annotations where they clarify which AST layer or record type is in use, especially where record labels overlap.
- Preserve `Loc.t` information through parsing and lowering. User-facing diagnostics should carry the most specific relevant source location.
- Report invalid user programs through the existing diagnostic model with an appropriate category and level. Reserve exceptions for parser boundaries, internal invariants, and genuinely unrecoverable failures.
- Follow the existing pass-state pattern when mutation is useful: keep mutable state local to the pass, accumulate diagnostics in reverse order, and reverse once when producing the result.
- Avoid broad utility modules or helpers for one-off logic. Add an abstraction only when it is reused or materially simplifies a complex transformation.
- Comments should explain non-obvious invariants, ordering constraints, or language semantics, not restate the code.

## Tests and verification

Use the narrowest relevant test during development, then run the broader gates appropriate to the change.

From the repository root, enter the pinned development environment when needed:

```sh
nix develop
```

From `src/`, the normal OCaml loop is:

```sh
dune build
dune runtest
dune fmt
```

Inspect the formatting diff after `dune fmt`; it promotes formatted files into the source tree.

The repository CI gates are:

```sh
nix build -L .#ocaml
nix flake check -L
```

Testing expectations:

- Put parser behavior in `src/test/test_parser.ml`, pipeline/lowering behavior in `test_pipeline.ml`, and analysis or LLVM behavior in the nearest dedicated test module.
- New test modules must be listed in `src/test/dune` and invoked from `src/test/test_src_ml.ml` through their `run` function.
- For a rejected program, assert the diagnostic category and meaningful message text, not only that some error occurred.
- For a language feature, include a positive case and relevant negative or boundary cases.
- For LLVM, ABI, ownership, or reference-counting changes, inspect the emitted IR and run a minimal compiled program when feasible. Use a small C harness for C ABI behavior that cannot be proven from IR alone.
- Do not claim the legacy compiler was validated unless you explicitly ran its gate, such as `nix build .#legacy`.
- If a required gate cannot run, report the exact command, failure, and remaining validation gap in the handoff or PR.

## Pull requests

- Keep each PR centered on one coherent change. The description should summarize behavior, tests run, and any known limitations or deferred work.
- When creating or updating a PR, apply exactly one provenance label:
  - `ai-generated` when the majority of the PR's code or content was generated by AI.
  - `human-generated` when the majority was written by a human, even if AI tools assisted.
- Also apply at least one change-category label:
  - `bug` for correcting incorrect behavior.
  - `documentation` for documentation-only or documentation-led changes.
  - `enhancement` for new capabilities or intentional behavior improvements.
- Use multiple category labels only when the PR genuinely spans those categories. Update labels if the scope changes during review.
- Apply labels as part of opening the PR and verify the final PR state. If permissions or tooling prevent labeling, state exactly which labels are needed in the handoff rather than silently omitting them.
- Do not add workflow labels such as `good first issue`, `help wanted`, `duplicate`, `invalid`, `question`, or `wontfix` to a PR unless the task explicitly calls for them.
